# W2-B13：基于上游的排队点击适配（离线完成）

2026-11-04，用户同意按最新上游实现做最小适配。**已实现并验证 MOVE → DOWN → 等待 → UP 的可注入提交组件，接通原有父进程持久意图及子进程协议；尚未注册真实微信排队发送后端，没有新增微信输入、消息或临时启用。D / V0 仍未通过。**

## 修改范围与来源

新增 `posted_click.py`，基于 whale_gril 提交 `0af4dcd5596192e0fa4d3938ea93b404771d6e02` 的 `bridge/bg_sender.py:421–446` 改写点击序列，保留默认至少 70ms 的按下等待。上游代码和许可摘要重新核对匹配；MIT 原文、版权及复用记录已放入可分发的 `assets/licenses/whale_gril-MIT.txt` 和 `whale_gril-source.json`，没有添加上游运行依赖或 import 上游 Win32 模块。

保持现有物理坐标和验证规则，使用已验证的客户区坐标编码，不复制上游失败时继续使用未验证 DPI 转换结果的逻辑。没有复制整套 `send()`，因此不带系统读屏设置、自动热启用、切会话、伪焦点、逐字符输入、编码试写/清框、剪贴板、全局键鼠、OCR 或失败回退。

`PostedClick` 的观察、投递、取消、记账、时钟和等待均由调用方注入，适配现有可终止工作进程。它当前只在合成工作进程和测试拥有的隐藏窗口中使用。现有 `wechat_native_worker.py` 的后端选择、默认拒绝策略及旧单次试验入口未修改，没有可从 CLI 启动的新微信发送路线。现有 `NativeDirectedTrial` 也没有被悄悄改成队列投递。

## 处理过程

1. BEGIN 先由父进程完整提交，再观察当前账号、规范 filehelper、原进程/窗口/线程、同一输入与按钮、完整草稿、焦点、几何、命中及无硬件干扰。
2. MOVE 单独写前记录，父进程确认后再次观察；然后只向原绑定接收者请求入队一次 MOVE。
3. DOWN 同样单独提交和复核，只请求一次。随后先等待至少 70ms，再在最长 0.5 秒、最多 32 次观察内等待当前按钮按下位。观察慢于期限也不能通过，时钟停滞也不会无限循环。观察调用本身的总耗时仍由外层工作进程超时和回收机制限制。
4. UP 前必须已观察到按下位，父进程持久确认后还要再次核对身份、草稿、几何及按下状态；变化便停止，不删除检查强行释放。
5. 完整请求仅返回 `REQUESTED / window_messages_enqueued_not_delivery`。它不证明 UP 已处理、队列已排空、编辑器已清空、数据库已有新回显或手机收到；这些必须由后续真实适配和验收提供。

真实 `post` 回调接入时仍须在实际 `PostMessageW` 前独立验证原 HWND/PID/创建时间/线程、固定程序及参数，关闭父进程 ACK、观察到原生调用之间的变化窗口。本轮测试发射器只接受自建测试窗口的精确类、PID、创建时间、线程和客户区点，拒绝其他窗口。真实微信发射器及提交后的双文本空输入检查尚未接线，不能以隐藏窗口的成功代替本机微信兼容证据。

## 未知结果与兼容

- 只要 MOVE 意图已提交，就不能把后续中断报告为完全未开始；MOVE-only 崩溃恢复也保留 UNKNOWN，禁止重放。
- DOWN 后的异常只尽力向原目标请求取消，不对新目标释放，不重试点击。取消即使成功入队，也只记 `CLICK_CANCEL_ENQUEUED`；不会写为同步取消已处理，更不证明 Qt 回滚。
- 结果新增可选的 `move_attempted`、`message_mode` 和 `cancel_enqueued`，旧六字段结果仍有原默认值；同步旧结果和队列结果分别校验。父子帧的意图上限由 4 调整为 5（BEGIN/MOVE/DOWN/UP/CANCEL），第六次拒绝。
- 主账本原有 journal 已可保存新阶段，无新表/迁移。新增 MOVE 顺序、单次使用、结果/意图一致性及排队模式记录；未观察到模式的中断不猜成同步通道。旧 UNKNOWN 不转成 FAILED 或 CONFIRMED。
- 暂停、过期、新消息及绑定检查仍由父进程在实际副作用许可时执行。MOVE 后暂停会阻止 DOWN；取消保留原有尽力清理例外。没有通道解锁、换账本或新请求绕过。

## 验证

新增 **33 个关键场景**：延迟处理、按下位缺失/丢失、ACK 后目标/输入变化、提交失败、暂停、子进程挂起回收、MOVE 后重启、队列取消及意图数量限制等。全量 **388 passed、848 subtests passed**（159.77 秒），相关源码及测试 Ruff 通过。

自建隐藏 HWND 实验将目标线程停在消息循环之前，先后投递 MOVE、DOWN、CANCEL，三个 API 都返回成功；此时没有处理记录。放行目标后才按序收到三条消息。这实际验证了“入队成功不是处理完成”，没有显示窗口或控制全局鼠标/键盘，更没有向微信发消息。目标进程最后由 Job 终止并核实无遗留子进程。

证据：[全量 JUnit](../.build/w2b13-upstream-full-2026-11-04.xml)、[本轮审计与摘要](evidence/w2b13-upstream-adapter-2026-11-04.json)。测试使用临时账本；真实发送账本仅 mode=ro 复查，仍为 4 次尝试、1 次已结束复核、累计各 2 次输入/提交许可、1 条历史手机确认、活动绑定 0 和 `submission_or_draft_requires_review`；完整性通过。

## 旧尝试与草稿的对账合同

这部分是接入前合同，不新增绕过 `channel_review.history()` 的入口：

1. 固定旧 action/operation、原始试验输出及手机“未看到”/电脑“有草稿”的观察。它们只说明当时未观察到送达；不伪造肯定确认，不把旧尝试改成 FAILED。
2. 旧草稿继续保留。若后续准备新现场试验，必须由用户明确决定旧草稿的处理方式；程序不得自动清空、覆盖、补点发送或复用旧标记。当前未请求用户清理。
3. 必须核对原工作进程已结束；若涉及曾入队但处理未知的消息，还须单独处理原目标进程/窗口代际和待处理队列。杀掉发送子进程、收到取消入队结果或看到按钮未按下，都不能替代这一步。
4. 未来即使由操作员接受旧不确定性，也应另记独立审核事实，保留旧 outbox/attempt 的 UNCONFIRMED；不能借用 `manual_confirmation` 假称送达。本轮没有实现这类新放行或更改真实账本。
5. 新现场方案需明确新的请求/正文、原生回调、提交后空输入/严格新回显和手机核对，并接受一次具体的新试验许可。上一次单次许可已消费，这次“同意改造”也不作为新发送许可。
