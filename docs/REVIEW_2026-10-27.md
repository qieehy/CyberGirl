## 发现的问题

### R1 / P1：指纹拒绝发生在覆盖旧框架 wheel 之后

位置：`scripts/build_framework.py:53–65`。

脚本先执行 `pip wheel --wheel-dir .build/wheels`，产物固定为 `ai_agent-0.3.0-py3-none-any.whl`，之后才比较 `framework.lock.json`。当框架内容发生变化但版本仍为 0.3.0 时，构建可以先替换已锁定的安装包，再以“fingerprint changed”退出，留下旧锁和新包不匹配的状态。当前相邻框架已经存在相对锁定快照的变化，这不是纯假设的使用路径。

隔离复现：使用临时合成源码及模拟构建器执行真实构建脚本，确认它在拒绝指纹变化前已经调用构建器并覆盖目标文件，锁文件却保持不变。当前真实 wheel 未改动，哈希仍与原锁一致。

建议：在构建前比较源码指纹和构建配置；将新产物写入独立候选目录，完成所有验证后才发布到锁定位置。任何拒绝路径都必须保留旧包。不要直接从已变化的相邻框架重建到现有 wheel 目录。

### R2 / P2：单次可恢复错误会结束整个聊天并清空上下文

位置：`src/wechat_agent/cli.py:71–95`、`:140–142`。

交互循环没有逐回合错误处理。输入校验、连接失败、超时、429 等 `ProviderError` 会离开循环，在 finally 中关闭应用，再由顶层直接退出。聊天历史只存在 RAM，因此重开终端无法恢复此前已经确认的对话。

离线复现：已安装 CLI 的 mock 模式先正常回答一轮，然后输入 8001 个字符；程序以退出码 1 报 `invalid_input`，后续有效输入没有被处理。无需网络故障就能触发。

建议：将可恢复错误限制在本回合，显示中文原因后继续等待输入，保留已确认历史；不要自动重发失败请求。认证失效、存储故障与用户明确退出另行处理。

### R3 / P2：失败验收记录缺少阶段和实际请求次数

位置：`src/wechat_agent/verification.py:32–75`、`:105–110`。

`run_probe` 只有成功返回时才交出 `model_http_attempts` 等上下文；一旦异常，外层仅记录错误码、状态码和 request ID。目录查询和推理都可能产生同类错误，失败记录无法说明推理是否已经开始，也无法保留 401 后第二次请求的计数。

现有 `.state/h4/provider.json` 和 `provider-v2.json` 已体现该缺口：两者都没有失败阶段及实际尝试数。H4 总结因此只能将最早失败的额外请求数记为 0–1，不能精确回溯。

建议：在执行前建立可持续更新的进度记录，明确 catalog / model / acceptance 阶段，在异常和取消路径的 finally 中保存实际尝试数。原始提示词、回答和凭据仍不写入诊断。
